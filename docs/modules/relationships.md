# Relationships / 关系页设计

> 状态：设计稿 v0.1  
> 日期：2026-11-20  
> 范围：实体关系页、关系展示、关系创建、关系 Tab 信息架构  
> 不包含：关系时间线系统、AI 自动抽取关系、复杂图谱、关系冲突审稿

---

## 1. 模块定位

关系不是实体详情里的一个普通字段。

在小说创作中，关系是故事复杂度的核心来源：

```txt
人物和人物之间的情感、利益、秘密
人物和势力之间的身份、立场、背叛
地点和势力之间的控制、争夺、管辖
道具和人物之间的拥有、继承、争夺
世界规则和实体之间的约束、例外、违反
```

因此，关系应成为实体详情中的独立页签，而不是继续挤在基础信息下方。

核心原则：

```txt
关系是实体网络，不是实体字段。
关系页是统一入口，不是各模块的小表单。
P1 先整理现有关系，不大改 schema。
P2 再增强专用关系创建。
P3 再接关系演化、图谱、AI 建议。
```

---

## 2. 与“时间变化”的边界

用户已确认：小说中的人物、地点、势力、关系都会随时间变化。

但 P1 不直接实现完整时间线系统。

本模块只保留未来演化所需的最小字段和设计边界：

```txt
startsAt
endsAt
isCurrent
canonStatus
说明文本
来源证据
```

关系演化、关系版本、章节范围、读者知情变化、角色知情变化，后续应统一进入更大的“状态演化 / 时间线 / 连续性”设计。

P1 关系页只回答：

```txt
当前有哪些关系？
这些关系来自哪里？
是否当前有效？
是否正史确认？
有没有起止阶段说明？
```

P1 不回答：

```txt
这个关系每一章如何变化？
谁什么时候知道这层关系？
读者什么时候知道？
关系变化是否造成连续性冲突？
```

这些后置。

示例：

```txt

共有 18 条关联
当前有效 14 条 · 草稿 3 条 · 已归档 1 条

[人物 5] [地点 2] [势力 4] [规则 3] [道具 2] [能力 2]
```

统计维度：

```txt
总关系数
当前有效数
草稿 / 已确认 / 已归档数
按目标类型统计
按关系来源统计
```

关系来源包括：

```txt
通用关系
成员关系
势力关系
地点控制
地点规则

物种规则
道具规则
```

## 6. 筛选区

筛选区位于概览下方。

```txt
[全部类型] [全部来源] [当前有效] [全部正史状态] [搜索对象或说明] [+ 新增关系]
```

筛选项：

| 筛选项 | 说明 |
|---|---|
| 目标类型 | 人物 / 地点 / 势力 / 物种 / 道具 / 能力 / 世界规则 / 世界设定 |

## 9. 新增关系流程

新增关系从关系 Tab 右上角进入。

```txt
+ 新增关系
```

表单流程：

```txt
目标类型
  -> 目标对象
  -> 关系类型
  -> 方向
  -> 强度
  -> 时间范围
  -> 说明
  -> canonStatus
```

表单示例：

```txt
新增关系

当前实体：林青 · 人物

目标类型：[人物]
目标对象：[搜索并选择...]
关系类型：[师徒]
方向：[林青 → 目标] [目标 → 林青] [双向]
强度：[弱 —— 中 —— 强]
开始阶段：[第一卷第 3 章]
结束阶段：[可选]
说明：[这段关系为什么重要？]
正史状态：[草稿]
```

P1 保存到 generic `Relationship`。

P2 再根据目标类型和关系类型引导到专用表。

## 12. Relationship 与专用关系表边界

### generic Relationship 适合

```txt
低频关系
跨实体弱关系
语义补充
证据引用
呼应关系
暂时没有专用表的关系
```

### 专用关系表适合

```txt
高频核心关系
需要专门字段的关系
会被 Context Builder 高频读取的关系
有清晰业务语义的关系
```

示例：

| 关系 | 推荐存储 |
|---|---|
| 人物属于势力 | FactionMembership |
| 势力敌对势力 | FactionRelation |
| 地点受势力控制 | LocationFaction |
| 地点适用规则 | LocationRule |
| 势力适用规则 | FactionRule |
| 物种适用规则 | SpeciesRule |
| 人物与人物是朋友 | Relationship |
| 人物拥有道具 | Relationship，后续可升级专用关系 |
| 事件呼应世界规则 | Relationship |

## 17. 面向 AI 的关系写入与建议机制

关系页后续不仅服务人工维护，也要开放给 AI 使用。

但 AI 不应直接绕过用户，把推测关系写成正式关系。关系是小说世界观的结构骨架，AI 只能进入“建议 / 草稿 / 待确认”流程。

### 17.1 AI 可以做什么

AI 后续可以：

```txt
从章节正文中发现关系
从场景摘要中发现关系变化
从 SceneHandoff 中发现开放关系
从人物/地点/势力设定中抽取潜在关系
发现某个实体缺少必要关系
建议某条关系进入 Context Builder
建议关系类型、方向、强度、说明
```

示例：

```txt
AI 发现：林青 与 青云宗 存在“成员”关系
证据：第一章中写到“林青通过试炼成为青云宗外门弟子”
建议存储：FactionMembership
状态：draft
置信度：0.86
```

### 17.2 AI 不能直接做什么

P1/P2 阶段，AI 不应直接：

```txt
自动创建 confirmed 关系
自动覆盖用户已确认关系
自动删除关系
自动合并实体
自动把“同场出现”当作强关系
自动把所有提及都变成 Relationship
```

AI 生成的关系必须默认进入：

```txt
draft
sourceType = ai_suggestion / scene_summary / chapter_summary / memory_record
sourceId = 对应来源 ID
confidence = 建议置信度（后续字段或建议队列承载）
```

### 17.3 AI 关系建议队列

后续建议新增“AI 关系建议”体验，但 P1 不实现。

建议卡片：

```txt
建议关系
林青 → 青云宗
类型：成员
建议存储：势力成员
来源：第一章摘要
证据：林青通过试炼成为青云宗外门弟子
置信度：86%

[确认] [修改后确认] [忽略]
```

确认后再写入正式关系表或专用关系表。

### 17.4 AI 写入路径

后续 AI 写入关系应走同一套 Service/API 边界，不能直接写数据库。

必须校验：

```txt
projectId 边界
目标实体存在且未软删除
关系类型是否适用于源/目标类型
是否命中专用关系表
是否存在重复关系
canonStatus 默认 draft
sourceType/sourceId 可追溯
```

### 17.5 Context Builder 如何使用关系

关系进入 Context Builder 时，不应全量注入。

应按任务读取：

```txt
当前 Scene 相关人物关系
当前地点相关势力/规则关系
当前 POV 角色的重要关系
当前章节涉及势力冲突关系
confirmed 关系优先
draft 关系默认不进入，除非用户显式选择
```

Context Builder 需要保留 sourceRefs：

```txt
Relationship
FactionMembership
FactionRelation
LocationFaction
LocationRule
FactionRule
SpeciesRule
StoryItemRule
AbilityRule
```

### 17.6 与未来时间体系的边界

AI 可能会发现“关系变化”，但 P1 不做关系时间演化。

AI 可以先生成建议说明：

```txt
林青和沈砚的关系从信任变为怀疑。
```

但不把它写成正式时间线事件。

关系变化、关系版本、读者/角色知情时间，后续进入独立的 Novel Time System / 状态演化设计。
